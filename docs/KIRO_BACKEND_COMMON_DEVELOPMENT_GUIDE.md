# InnerDerma Backend --- Kiro 공통 개발 가이드

목적: 반복 지시를 줄이고, 안전한 연속 개발과 정책 일관성을 유지하기 위한
상시 규칙

## 1. 이 문서의 우선순위와 사용법

Kiro는 백엔드 개발을 시작하거나 이어갈 때 이 문서를 공통 작업 규칙으로
적용한다. 기능별 상세 기획서·최종 요구사항·현재 코드가 이 문서보다
구체적인 경우 그 근거를 우선하되, 서로 충돌하거나 새로운 정책 결정이
필요한 경우 임의로 결정하지 않고 사용자에게 확인한다.

-   이 문서는 '어떻게 개발할지'를 정하는 공통 가이드다.

-   인수인계/진행상황 문서는 '현재 어디까지 개발됐는지'를 기록하는 별도
    문서로 취급한다.

-   이미 확정된 기능 정책은 해당 정책 문서와 코드/테스트를 근거로
    유지한다.

-   새 기능을 시작할 때마다 이 문서를 다시 장황하게 설명하지 말고 바로
    적용한다.

## 2. InnerDerma 서비스 기준

InnerDerma는 한국에서 AAC의 피부 시술·피부 진단·웰니스 서비스를 이용한
외국인 고객이 귀국한 뒤에도 진단/시술 이력과 현재 상태를 바탕으로
개인화된 사후관리 케어를 이어갈 수 있도록 하는 모바일 서비스다.

-   시술 후 반드시 지켜야 하는 사후관리 항목과 일반적인
    제품·콘텐츠·웰니스 추천을 구분한다.

-   백엔드는 진단·시술·자가문진·피부 상태·추세·규칙 결과를 구조화하고
    결정적 케어 산출의 기반을 제공한다.

-   LLM은 결정적 규칙/데이터를 대체하지 않는다. 필요 시 설명·표현
    계층으로 사용한다.

-   의료 진단, 임상적 위험도, 효능, 회복기간 등 근거 없는 판단을 코드나
    LLM이 임의 생성하지 않는다.

## 3. 기본 개발 실행 원칙

일반적인 개발 작업은 사용자 확인을 기다리지 않고 연속으로 진행한다.

1.  미구현 기능 또는 현재 승인된 다음 기능을 선택한다.

2.  각 기능은 별도의 feature 브랜치에서 작업한다.

3.  기존 코드와 최종 기획/문서를 확인하고 구현한다.

4.  코드를 실행하고 관련 테스트를 수행한다.

5.  오류가 발생하면 원인을 분석하고 수정한 뒤 다시 테스트한다.

6.  관련 테스트 통과 후 전체 회귀 테스트를 실행한다.

7.  기능 관련 파일만 stage하고 commit한다.

8.  GitHub origin의 해당 feature 브랜치에 push한다.

9.  push 후 브랜치명, commit hash, 테스트 결과만 한국어로 간단히
    보고한다.

10. 위험 작업이나 새 정책 결정이 없다면 사용자 답변을 기다리지 않고 다음
    미구현 기능 개발을 계속한다.

## 4. 브랜치 및 Git 원칙

-   기능 하나당 별도의 feature/\* 브랜치를 사용한다.

-   feature 브랜치 commit 및 origin feature 브랜치 push는 일반 개발
    작업으로 진행한다.

-   이미 push된 feature 브랜치는 작업 보존 지점으로 취급한다.

-   현재 개발 단계에서는 main/master/develop 또는 integration 브랜치로
    기능을 모으지 않는다.

-   핵심 기능 개발과 수정이 대부분 끝난 뒤 마지막 통합 단계에서 병합
    전략을 다시 결정한다.

-   브랜치가 의존 스택으로 쌓여 있어도 개발 중에는 억지로 main에
    수렴시키지 않는다.

-   기존 feature 브랜치의 이력을 파괴하거나 이미 push한 기능을 되돌리는
    작업은 반드시 확인한다.

## 5. 반드시 멈추고 사용자에게 확인할 위험 작업

다음 상황에서는 작업을 실행하지 말고 이유·영향·선택지를 설명한 뒤 사용자
확인을 기다린다.

-   main/master/develop 등 공유 브랜치에 merge 또는 push가 필요한 경우

-   force push가 필요한 경우

-   rebase가 필요한 경우

-   reset --hard가 필요한 경우

-   원격 브랜치 삭제 또는 branch -D 등 강제 브랜치 삭제가 필요한 경우

-   이미 GitHub에 push한 기능을 되돌리거나 이력을 변경해야 하는 경우

-   실제 MySQL DB의 데이터 또는 스키마를 변경해야 하는 경우

-   비밀번호, API Key, token 등 secret을 생성·조회·변경·노출해야 하는
    경우

-   최종 기획서와 기존 코드만으로 결정할 수 없는 새로운 정책/비즈니스
    규칙을 정해야 하는 경우

-   기존 작업을 삭제하거나 복구가 어렵거나 파괴적인 변경이 필요한 경우

### 위험 작업이 아닌 예

-   코드 조회/검색, 일반 파일 읽기, Git 상태/로그/diff 조회

-   feature 브랜치 생성, 일반 add/commit, origin feature 브랜치 push

-   Gradle 빌드·테스트 및 테스트 오류 수정

-   H2 인메모리 테스트 DB에서 create-drop으로 엔티티 매핑을 검증하는
    작업

-   프로덕션 DB에 연결하지 않는 순수 단위/통합 테스트

## 6. 정책 결정 처리 규칙

-   문서와 기존 코드로 결정 가능한 것은 질문하지 말고 구현한다.

-   단순 구현 선택(클래스명, 내부 메서드 분리 등)은 기존 패턴에 맞춰
    결정한다.

-   사용자 경험, 데이터 의미, 임계값, 의료/안전 해석, 저장 정책 등
    비즈니스 의미가 달라지는 결정은 임의로 만들지 않는다.

-   정책 결정이 필요하면: 결정 내용 → 필요한 이유 → 현재 상태 → 문서
    근거 → 애매/충돌 → 선택지 → 장단점 → 추천 → 후속 영향 → 변경 난이도
    순으로 정리한다.

-   사용자가 확정한 정책은 이후 같은 사안을 반복해서 다시 묻지 않는다.

## 7. 의료·안전·AI 규칙

-   자가문진 severity, 피부 분석 점수, trend 등은 원천 데이터 또는
    결정적 계산값으로 취급한다.

-   SEVERE 입력 자체를 의료적 위험·진단·전문가 진료 필요로 자동 해석하지
    않는다.

-   문서에 없는 임상 임계값, 위험 기준, 효능, 용량, 회복기간을 만들지
    않는다.

-   Signal 계층은 사실만 표현하고, 해석은 명시된 Rule 계층에서만
    수행한다.

-   정의된 산출 소스가 없는 signal은 추론해서 만들지 않고 미설정/false로
    둔다.

-   LLM이 사용되더라도 Rule Engine/결정적 Solution 결과를 임의로
    변경하지 못하게 한다.

## 8. 현재 확정된 AI 파이프라인 원칙

현재 개발 방향은 다음의 결정적 파이프라인을 기본으로 한다.

``` text

Skin/Procedure/SelfCheck Data
→ Skin State Snapshot
→ Trend
→ SignalAssembler
→ Rule Engine
→ Solution Object
→ (후속) 사용자 대면 Care/LLM 설명 계층
```

-   Snapshot: 자가문진 원천 축을 보존하고 scoringVersion을 저장한다.

-   Trend: 같은 scoringVersion의 최신 2개를 비교하며 delta 방향으로
    improving/stable/worsening을 결정한다.

-   SignalAssembler: 이미 계산된 결정적 사실만 RuleEvaluationContext로
    변환한다.

-   Rule Engine: category pipeline order → priority 순으로 실행하며
    ruleId는 참조 식별자로 사용한다.

-   Solution Object: 현재는 비영속 in-memory 내부 결정 결과로 유지한다.

-   CareSolution과 SolutionObject는 현재 독립 유지한다. 기존
    CareSolution API/DB/프론트 계약을 당장 교체하지 않는다.

-   Solution Object를 영속화하거나 CareSolution DB에 applied_rules를
    저장하는 작업은 실제 필요가 확정될 때 별도 결정한다.

## 9. 기존 API와 프론트 계약 보호

-   기존 API URL, Response DTO, 필드 의미를 불필요하게 깨지 않는다.

-   내부 구현 개선만으로 해결 가능한 경우 외부 계약은 유지한다.

-   기존 CareSolution 사용자 흐름은 새 AI 파이프라인이 안정화되기 전까지
    보존한다.

-   프론트 계약을 변경해야 하는 경우 영향 범위를 먼저 보고하고 정책
    확인을 받는다.

-   UI 텍스트 다국어는 기본적으로 프론트엔드 범위이며 백엔드 MVP 잔여
    기능으로 계산하지 않는다.

-   향후 LLM 사용자 문장 생성에 언어 정보가 필요할 경우 최소 locale
    전달만 별도 검토한다.

## 10. DB 및 데이터 원칙

-   테스트는 테스트 전용 설정(H2 등)을 사용하고 실제 MySQL을 변경하지
    않는다.

-   새 @Entity 추가가 실제 애플리케이션 기동 시 MySQL 스키마 변경을
    유발할 수 있다면 실제 기동 전에 확인한다.

-   ddl-auto에 의존한 실제 운영 DB 자동 변경을 임의로 실행하지 않는다.

-   데모/목업 데이터는 실제 AAC 운영 데이터와 구분한다.

-   DB migration/스키마 변경이 필요해지면 변경안과 영향 범위를 먼저
    제시한다.

## 11. 테스트 및 품질 기준

-   새 기능에는 성공 케이스뿐 아니라 주요 실패/경계 케이스 테스트를
    포함한다.

-   관련 테스트 통과만으로 끝내지 않고 가능한 범위에서 전체 회귀
    테스트를 수행한다.

-   테스트 실패를 숨기거나 제외하여 성공 처리하지 않는다.

-   새 의존성 추가가 필요한 경우 기존 의존성/패턴으로 해결 가능한지 먼저
    확인한다.

-   테스트 전용 의존성 하나 때문에 제품 구조를 불필요하게 확대하지
    않는다.

-   완료 보고에는 실제 통과한 테스트와 전체 실패 여부를 정확히 적는다.

## 12. 터미널/승인창 최소화 원칙

-   가능하면 이미 Trusted/Always allow 된 안전한 명령 형식을 재사용한다.

-   여러 명령을 ;, \|, &&, Out-Null, 2\>&1 등으로 과도하게 결합하지 말고
    단일 명령으로 실행한다.

-   조회 결과를 임시 파일로 저장하는 복합 PowerShell 명령은 꼭 필요한
    경우에만 사용한다.

-   안전한 조회/빌드/테스트가 승인창 때문에 반복 실패하면 동일 패턴을
    무한 반복하지 말고 더 단순한 명령으로 바꾼다.

-   승인 실패 루프에 빠지면 개발 로직 문제가 아니라 실행 방식 문제인지
    먼저 판단한다.

-   Kiro가 스스로 Always allow 버튼을 선택할 수 있다고 가정하지 않는다.
    승인 UI는 사용자가 제어한다.

## 13. 언어 및 보고 형식

-   진행상황 설명, 질문, 정책 결정 보고, 완료 보고는 한국어로 작성한다.

-   일본어 등 다른 자연어를 섞지 않는다. 코드/API/클래스/Git 명령 등
    기술 영문은 그대로 사용한다.

-   feature push 완료 보고는 아래 3가지를 중심으로 짧게 작성한다.

``` text

브랜치: feature/...
commit hash: abc1234
테스트: 관련 테스트 N개 통과, 전체 실패 0
```

-   '다음 개발을 이어갈까요?'처럼 일반 개발 진행 여부를 묻지 않는다.

-   새 정책 결정이나 위험 작업이 있을 때만 질문한다.

## 14. 개발 우선순위 원칙

-   자잘한 조회 API를 무한히 늘리기보다 InnerDerma 핵심 사용자 플로우의
    end-to-end 완성을 우선한다.

-   현재 핵심 AI 파이프라인의 결정적 계층을 안정화한 뒤 사용자 대면
    Care/LLM 계층을 연결한다.

-   기능 개발이 계속될 가능성이 높은 동안 main/integration 통합은
    미룬다.

-   중복 feature가 발견되면 둘 다 병합하지 말고 구현/테스트/기획 근거를
    비교한 뒤 채택안을 결정한다.

-   기획에 없는 기능을 '완성도를 위해' 임의 추가하지 않는다.

-   MVP 완료 기준과 무관한 작업은 별도 후속 항목으로 둔다.

## 15. Kiro가 작업 시작 시 적용할 짧은 지시문

새 세션 또는 컨텍스트가 끊긴 뒤에는 아래 문장과 이 문서를 함께 기준으로
삼는다.

``` text

KIRO_BACKEND_COMMON_DEVELOPMENT_GUIDE를 공통 개발 규칙으로 적용해.
최종 기획서, 현재 코드, 이미 확정된 정책을 근거로 연속 개발을 진행하고,
문서에 정의된 위험 작업 또는 새로운 비즈니스 정책 결정이 필요한 경우에만 멈춰 확인해.
현재는 main/integration 병합 단계가 아니며 feature 브랜치에서 개발·테스트·commit·origin push를 계속해.
```

## 16. 이 문서에 넣지 않는 것

-   특정 기능의 일회성 구현 세부사항

-   현재 commit hash/브랜치별 진행률처럼 계속 바뀌는 상태 정보

-   일시적인 오류 로그

-   아직 확정되지 않은 정책을 확정사항처럼 기록하는 내용

-   main 최종 병합 순서처럼 개발 완료 시점에 다시 판단해야 하는 내용

이런 정보는 인수인계/진행상황 문서 또는 기능별 설계 문서에 기록한다.
공통 가이드는 자주 바뀌지 않는 작업 방식과 안전 경계만 유지한다.
